# Deployment guide

Three pieces, all on free tiers to start:

| Piece | Where | What runs |
|---|---|---|
| Database | **Neon** (Postgres, region `ap-south-1` Mumbai) | patients, encounters, reviews, consents, audit log |
| API | **Render** (Docker web service) | `ayurnidaan.app.main:app`, runs migrations on every start |
| Website | **Vercel** (static) | the Expo app exported for web (`mobile/`) |
| Android app | **EAS Build** → **Google Play** | the same Expo app, built as an `.aab` |

Health data stays in India if you pick Neon's Mumbai region. Render's nearest region
is Singapore; the API holds no data at rest, but if you need data processing in India
too, use Google Cloud Run in `asia-south1` with the same Docker image.

---

## 0. Push to GitHub

```bash
cd ayur-analytics
git init && git add . && git commit -m "Ayurnidaan clinical platform"
git branch -M main
git remote add origin https://github.com/<you>/ayurnidaan.git
git push -u origin main
```

`.gitignore` already excludes the raw Kaggle data (one file contains real names),
local databases, `.env`, `node_modules` and build outputs. The PII-free
`knowledge_pack/` **is** committed: the API runs on it.

GitHub Actions then runs the full CI + security pipeline on every push: tests, lint,
migration drift, secret scanning, SAST, dependency audits, the container scan and a
DAST scan. Production deploys happen **only** through `cd.yml`, after all of it passes.
[docs/PIPELINE.md](docs/PIPELINE.md) explains each gate and the one-time GitHub setup
(secrets, environments, branch protection).

## 1. Database (Neon)

1. neon.tech → New project → region **AWS Asia Pacific (Mumbai)**.
2. Copy the connection string (`postgresql://…?sslmode=require`).

## 2. API (Render)

1. render.com → **New → Blueprint** → select the repo (it reads `render.yaml`).
2. When prompted, set:
   - `AYUR_DATABASE_URL` = the Neon string
   - `AYUR_CORS_ORIGINS` = `["https://<your-vercel-domain>"]` (set after step 3; redeploy)
   - `AYUR_BOOTSTRAP_ADMIN_EMAIL` = your email (the first account registered with it becomes admin)
   - `AYUR_JWT_SECRET` and `AYUR_PII_SALT` are generated by Render.
3. Deploy. Check `https://<service>.onrender.com/ready` → `{"database": true, ...}`.
4. Auto-deploy is **off** (`render.yaml`), so a push alone never ships. Copy
   *Settings → Deploy Hook* into the GitHub secret `RENDER_DEPLOY_HOOK_URL`. From then on,
   `cd.yml` triggers the deploy after CI passes, waits for the new commit to be live
   (`/health` reports it), and smoke-tests it.

The app refuses to start in production with development secrets or SQLite.
Free Render services sleep after 15 minutes idle; the first request then takes ~30 s.

## 3. Website (Vercel)

1. vercel.com → Add project → import the repo → **Root directory: `mobile`**.
2. Environment variable: `EXPO_PUBLIC_API_URL` = `https://<service>.onrender.com`.
3. If your API URL is not `https://ayurnidaan-api.onrender.com`, change it in **two**
   places: `eas.json`, and the `connect-src` of the Content-Security-Policy in
   `mobile/vercel.json`. Otherwise the browser blocks every API call.
4. Production deploys come from `cd.yml`. Vercel's own Git deploys are disabled for
   `main`, but PR previews still work. Run `npx vercel link` in `mobile/` once, then add
   `VERCEL_TOKEN`, `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` (from `mobile/.vercel/project.json`)
   as GitHub secrets. For the very first deploy you can also run `npx vercel --prod`.
5. Add the Vercel URL to `AYUR_CORS_ORIGINS` on Render and redeploy the API.
6. Register with your bootstrap email → you are admin. Register a practitioner account
   in another browser and verify it from the admin screen.

## 4. Android (EAS → Google Play)

```bash
cd mobile
npx eas-cli@latest login
npx eas-cli@latest init                      # links the project to your Expo account
# put your Render URL in eas.json (preview + production env), then:
npx eas-cli@latest build -p android --profile preview      # installable APK for testing
npx eas-cli@latest build -p android --profile production   # .aab for Google Play
```

### Google Play checklist

1. **Developer account** – play.google.com/console, one-time US$25, identity verification.
2. **Create app** → name *Ayurnidaan*, app (not game), free.
3. **Privacy policy URL** → `https://<vercel-domain>/privacy` (the app ships this page;
   have it reviewed by a lawyer and fill in the grievance officer).
4. **App content**
   - *Health apps declaration*: health & fitness / medical reference. Do **not** claim
     to diagnose; the app is screening + decision support with practitioner confirmation.
   - *Data safety*: collects name, email, health info, approximate location; encrypted
     in transit; users can request deletion (in-app: Profile → Delete account); not shared
     with third parties; not used for ads.
   - *Target audience*: 18+. *Ads*: none. *Content rating*: complete the questionnaire.
5. **Testing** – new personal developer accounts must run a **closed test with at least
   12 testers for 14 continuous days** before production access. Upload the `.aab` to
   the closed-testing track (`npx eas-cli@latest submit -p android` sends it to the
   internal track configured in `eas.json`).
6. **Production** – after the closed test, apply for production access and roll out.

## 5. Before real patients use it

These are not code tasks, and they matter more than any of the code:

- **Regulatory**: software that suggests diagnoses can be a medical device under India's
  Medical Devices Rules 2017 (CDSCO). Get a regulatory opinion before public launch;
  keeping it practitioner-in-the-loop (as built) is the safer classification.
- **Clinical validation**: the engine's accuracy figures come from simulated textbook
  patients. Run a supervised pilot with practitioners, compare against their diagnoses,
  and use the learning loop only after you have that baseline.
- **Practitioner verification**: verify registration numbers against the State Board /
  NCISM register before approving accounts.
- **DPDP Act 2023**: appoint a grievance officer, keep the consent ledger, honour export
  and erasure requests (both are built in), and sign a data-processing agreement with
  Neon/Render.

## Operations

| Task | Command |
|---|---|
| Rebuild knowledge pack after data changes | `ayur run` then commit `knowledge_pack/` |
| Refresh literature evidence | `ayur build-evidence` then `ayur run` |
| Re-measure the engine | `ayur benchmark` (writes into the manifest) |
| New DB migration | edit `app/models.py`, then `alembic revision --autogenerate -m "..."` |
| Retrain from confirmed cases | Admin screen → *Retrain* (promotes only if not worse) |
| Local production-like stack | `docker compose up --build` |
| Release (image + Android build + GitHub Release) | `git tag v1.3.0 && git push origin v1.3.0` |
| Check a live deploy | `python scripts/smoke.py --production --api <api-url> --web <web-url>` |
